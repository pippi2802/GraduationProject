# dra-rt-driver v0.1.1 — CDI device-resolution fix

**Image:** `pippina2/dra-rt-driver:v0.1.1`
**Status:** deployed (current cluster image)
**Scope:** CDI per-claim spec resolution only — does **not** enable RT bandwidth enforcement.

---

## The problem it fixed

On the cloud node, containerd runs with **`enable_cdi=true`**. In the DRA flow the kubelet
plugin advertises a **per-claim CDI device** to the kubelet, named (in `cdi.go`
`GetClaimDevices`):

```
QualifiedName(rtCDIDevices[0], "CPUSET", rtCDIDevices[1])
=> "runtime-<R>.period-<P>/CPUSET=<cpuset>"
```

For containerd to actually inject that device, it must find a **matching CDI spec file on
disk** in the CDI root (`/var/run/cdi`). In the original driver that backing spec was not
written in a form that matched the advertised device name, so containerd could not resolve
it:

- Symptom: pod stuck in **`ContainerCreating`** / rejected with **"unresolvable CDI devices"**.
- Net effect: rt-DRA pods **never reached Running**, even though allocation (NAS) and cpuset
  math were correct.

The code documents the failure mode in the comment block of `CreateClaimSpecFile`:

> *"Without this spec on disk, a CDI-enforcing containerd rejects the pod with 'unresolvable
> CDI devices'."*

---

## Root cause, verified against upstream

Diffed against upstream `nasim-samimi/dra-rt-driver` (`cmd/dra-rt-kubeletplugin/cdi.go`,
branch `main`). The upstream `CreateClaimSpecFile` has **two defects**:

```go
func (cdi *CDIHandler) CreateClaimSpecFile(claimUID string, devices *PreparedCpuset, rtCDIDevices []string) error {
	// specName := cdiapi.GenerateTransientSpecName(cdiVendor, cdiClass, claimUID)  // commented out
	spec := &cdispec.Spec{
		Kind:    cdiKind,            // "k8s.rt.resource.example.com/cpu"  (the COMMON kind)
		Devices: []cdispec.Device{},
	}
	...
	for _, device := range devices.RtCpu.Cpuset {
		cdiDevice := cdispec.Device{
			Name: "cpu" + strconv.Itoa(device.id),   // device named "cpu<id>"
			ContainerEdits: ...{ Env: []string{ "RT_DEVICE_<idx>=<id>" } },
		}
		spec.Devices = append(spec.Devices, cdiDevice)
	}
	...
	// return cdi.registry.SpecDB().WriteSpec(spec, specName)   // <-- WRITE COMMENTED OUT
	return nil                                                  // <-- returns without writing
}
```

1. **It never writes anything to disk** — the `WriteSpec` call is commented out and it just
   `return nil`.
2. Even if it had written, the spec's `Kind` is the *common* `cdiKind` and the device names
   are `cpu<id>` — which **do not match** what `GetClaimDevices` advertises to the kubelet:
   `runtime-<R>.period-<P>/CPUSET=<cpuset>`.

So with `enable_cdi=true`, containerd asks for `runtime-<R>.period-<P>/CPUSET=...`, finds **no
matching spec on disk** → **"unresolvable CDI devices"** → pod stuck in `ContainerCreating`.

(Note: upstream's history is not present as a parent commit in this repo — `cdi.go` was
committed as a new file in `55efd0d` — so this delta is established by fetching the upstream
file directly, not via `git diff`.)

## What concretely changed in the logic (v0.1.1)

The fix lives in `CreateClaimSpecFile`: it now **actually writes** a per-claim transient CDI
spec whose **`Kind` + device `Name` exactly match what `GetClaimDevices` advertises**
(upstream returned `nil` without writing, and used a mismatched `Kind`/`Name`):

| Field | Value written | Why |
|---|---|---|
| `specName` | `GenerateTransientSpecName(cdiVendor, cdiClass, claimUID)` | one spec file per claim in `/var/run/cdi` |
| `Kind` | `rtCDIDevices[0] + "/CPUSET"` → `runtime-<R>.period-<P>/CPUSET` | must equal the advertised qualified name |
| `Device.Name` | `rtCDIDevices[1]` (the cpuset, e.g. `1` or `1-2`) | the device the kubelet asks containerd to resolve |
| `ContainerEdits.Env` | `RT_RUNTIME_PERIOD=<runtime-R.period-P>`, `RT_CPUSET=<cpuset>` | injected into the container |
| write | `cdi.registry.SpecDB().WriteSpec(spec, specName)` | the spec is now actually persisted to disk |

Plus a **guard**: if `rtCDIDevices == nil || len < 2`, it returns an error instead of writing
a malformed spec.

**Result:** the advertised device now has a backing spec on disk → containerd resolves it →
cpuset + `RT_*` env get injected → pods go **1/1 Running**.

A later commit (`425c30a`) only added `rtlog(...)` tracing around this path and error-handling
on `WriteSpec` — no behavioral change.

---

## Scope / what v0.1.1 did NOT do

- It does **not** enable RT bandwidth enforcement — the container still gets only a cpuset
  pin, no `cpu_rt_runtime_us` (the subject of `FINDING-cgroupv2-no-rt-enforcement.md`, and the
  target of v0.1.2).
- It does **not** include the prepare-race / stale-NAS-cache fix ("Solution 1") nor the CDI
  spec-version floor — those are the v0.1.2 changes.

---

## One-line summary

v0.1.1 = *"make the per-claim CDI spec on disk match the advertised device so
`enable_cdi=true` containerd stops rejecting the pod"* — purely a CDI device-resolution fix
that gets pods to Running; it does not touch RT scheduling.
