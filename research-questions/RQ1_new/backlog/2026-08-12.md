# Backlog — 2026-08-12

## Done today

**Adapted `model4-m` to use `requestedCpus` — and hit the case `rt-test1` never exercised**

Requested `[1, 3]` — a physically-separated pair (siblings are `(0,1)`/`(2,3)` on this hardware, `KEEP_CPU=0` stays excluded) — to replace `run_job.sh`'s old delete/recreate-until-landed retry loop for model4's "two distinct physical cores" requirement. This is a genuinely different case from yesterday's `rt-test1` validation: every cpu pair this driver has *ever* allocated before today happened to be numerically consecutive (siblings, or worst-fit picks that landed adjacent by chance), and `rt-test1` itself only ever requested one cpu per claim. `[1, 3]` was the first non-consecutive, multi-cpu request this codebase had ever actually processed — and it turned out three completely separate places were silently relying on that coincidence.

**Bug 1 — `job.yaml`'s own `RT_CPUSET` shell normalization (all three model4 variants)**
Written 2026-08-09 to fix a *different* bug (`"3-2"` instead of `"2-3"` breaking `taskset`), that fix diagnosed the symptom correctly but the cause wrong: it assumed the driver's hyphen-joined cpu list was a reversed *range* and `seq`-expanded it. For a genuinely consecutive pair, "reversed range" and "hyphen-delimited pair" normalize to the same result by coincidence. For `"1-3"`, they don't — `seq 1 3` silently produces three cpus (`1 2 3`) instead of the two actually allocated. Fixed by treating hyphens as plain delimiters (same as commas) everywhere, never a range — this also correctly simplifies the original reversed-pair case too (`"3-2"` → `"2,3"` directly, no range logic needed at all).

**Bug 2 & 3 — two reactive driver-side fixes, both wrong, both reverted**
Before finding the real cause, chased this at the driver level in `cdi.go` (`WriteCgroupToCDI`):
- `v1.0.1`: changed the cpu-list separator from hyphen to comma. Broke immediately — that same string doubles as a CDI *device name* elsewhere in the same function, and CDI's spec forbids commas in device names (`invalid character ',' in device name "1,3"`).
- `v1.0.2`: split into two separate strings (comma-joined for the env var, underscore-joined for the CDI name). Got further, but broke a **third**, previously undiscovered consumer: the pod started, then `runc` failed with `resources.CPU.Cpus="1_3" conversion error` — something upstream of runc was reading the CDI device *name* directly and expecting native cgroup cpuset syntax.

Traced that third consumer by checking the forked `containerd` checkout (`~/Documents/rt-k8s/containerd`, branch `rt`) — found `pkg/cri/server/container_create.go`'s `ExtractCDI`:
```go
cpus := strings.Replace(cpuset[1], "-", ",", -1)
```
The original hyphen-joined device name was **always correct** — `ExtractCDI` already translates hyphen-to-comma before handing the cpuset to `oci.WithCPUs`. Neither `v1.0.1` nor `v1.0.2` fixed a real bug; both broke a working translation that had been sitting there the whole time. Reverted `cdi.go` completely back to its original single-hyphen-builder form.

**Bug 4 (same root cause, one more location) — `run_job.sh`'s own `expand_cpuset()`**
Even after `job.yaml` and `cdi.go` were both correct, the pod kept starting successfully and then getting killed ~15s later. Cause: `run_job.sh`'s model4 physical-pair verification (`mt_cpus=$(expand_cpuset "$tgt_cpuset")`, checking the landed pair really is on two different physical cores) calls a **separate** shell function with the identical hyphen-as-range bug — reading the driver's `"1-3"` as three cpus, finding `mt_n=3 != MT_THREADS=2`, and endlessly re-placing an already-correct allocation until `PIN_ATTEMPTS` ran out and it gave up on the cell. Fixed the same way, confirmed safe to change globally (the function's other caller, `siblings_of`, already strips hyphens to spaces before calling it, so its behavior was unaffected either way).

**Root-cause lesson, worth remembering**: a shared string value with more than one consumer needs *every* consumer checked before declaring a fix done, not just the one currently throwing a visible error. Three of four bugs found today were each "fixed" once by patching the layer that happened to be erroring, which silently broke a different layer that had been relying on the exact same value in a different way. The actual fix was one location (`job.yaml` + `run_job.sh`'s `expand_cpuset`, both harness-side); two driver-side changes were pure churn, reverted.
