primes rounds use `_primes_roundN` exclusively, same convention already

## model4 — supervisor's redesign, scoped and started

Clarified with Silvia what the 2026-08-13 meeting notes actually meant:

- **Complete replacement**, not a fifth model alongside the old one. Nothing
  carried over from the old model4 (IRQ steering, self-contention,
  ptrchase/primes-as-the-interesting-variable) -- this model4 is entirely
  about the **activation mechanism**, not the workload kernel.
- **Core question**: periodic (timer-driven, precomputed schedule) vs
  event-triggered (externally/asynchronously triggered) activation -- how
  much release jitter does each produce.
- **Scope now**: measurement and demonstration only. Reduction/stabilization
  work is explicitly a later phase, not started.
- **"Provide stability to the environment"** clarified as a methodology
  requirement (the same `isolcpus`/node-prep isolation discipline every
  other model already gets), not a jitter-reduction goal for this phase.

**Implemented in `matmul.c`**: new `--activation periodic|event` flag.
`periodic` is the existing `clock_nanosleep`-against-precomputed-schedule
path, byte-for-byte unchanged. `event` is new: requires `--threads 2`
(`cpu-list[0]`=target, `cpu-list[1]`=generator). A generator thread fires
triggers at intervals uniformly jittered around `period_ns` (range
`[0.5, 1.5) x period_ns`, bounded rather than an unbounded-tail Poisson
process, deterministic from `--seed`), delivered to the target via a
condition variable -- a real async block/wake path (futex-based under the
hood), not a poll. The generator stamps its own send time into the shared
trigger state; the target reads that back as `release_ns` on wakeup. Same
CSV schema/columns as every other mode, so `dispatch_latency_us` becomes
the direct release-jitter comparison between the two activation mechanisms
with no new analysis tooling needed.

**Bug found and fixed during smoke-testing**: the generator originally
advanced its own schedule from the *actually observed* wake timestamp
(`send_ns`) rather than the *planned* one (`next_ns`) -- letting small real
OS scheduling noise in the generator's own wakeup compound into permanent
schedule drift across a run, and breaking the project's seed-determinism
convention (two runs at the same `--seed` should draw the same jitter
sequence). Fixed by advancing from `next_ns` (matching exactly how the
periodic path already does this), while `send_ns` still correctly reports
the real observed release time to the target.

**Also corrected my own initial test**: after the fix, `release_us` still
isn't byte-identical across two runs at the same seed -- and that's
correct, not a remaining bug. `release_us` in event mode is a genuine
observed clock timestamp (same category as `start_us`/`finish_us`, which
have never been exactly reproducible anywhere in this tool -- that's what
makes `cv` meaningful at all). What should be reproducible is the
*jitter-multiplier sequence* drawn from the seed, not the resulting
wall-clock values; verifying that specific thing still needs a small debug
hook that hasn't been built yet.
