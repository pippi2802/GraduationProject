**Replaced the ptrchase workload with a primes (trial-division primality) kernel**

Per the supervisor meeting notes (backlog/2026-08-13.md, point 2): ptrchase
(memory/LLC pointer-chase) retired entirely, replaced with a genuinely
data-dependent kernel while keeping the harness's existing reproducibility
guarantee (fixed seed -> identical candidate stream every run).

**Kernel design (`matmul.c`)**
- New `KIND_PRIMES`, selected via `--kind primes` (was `--kind ptrchase`).
- Trial-division primality test: candidates are odd integers drawn
  deterministically (seeded xorshift64, same generator as A/B matrix fill)
  from `[1000003, 2000003)`. Each candidate is tested by odd divisors
  3,5,7,... with a genuine EARLY EXIT on the first factor found -- unlike
  matmul's fixed-iteration loop, this is real data-dependent control flow
  (a composite with a small factor is cheap, a prime pays the full
  `sqrt(candidate)` trial).
- One K-unit = `PRIMES_CANDS_PER_K` (1024) candidates. Reproducibility comes
  from the candidate stream being deterministic, not from a fixed op count:
  a given K always tests the same candidates, in the same order, every run,
  so total work is identical run-to-run even though it isn't a closed-form
  count independent of the data (unlike matmul's `K * M^3` or old ptrchase's
  `K * HOPS_PER_K`).
- `ptrchase()`/`build_cycle()` and the `cbuf`/`chase_pos`/`buf_kb` machinery
  removed. `--buf-kb` kept as an accepted-but-unused CLI flag (cli
  compatibility with generate_yaml.py/calibrate.py, which still pass it
  unconditionally for any non-matmul workload).

**Empirical finding: intrinsic variance is real and can't be batch-averaged
away at RT-scale periods**
Measured cv at `PRIMES_CANDS_PER_K=32`: 0.28-0.39 (way above the existing
0.02-0.05 calibration gate). Increased to 1024: cv drops to 0.11-0.26, still
above threshold. Computed the batch size needed to reach cv~0.05 via
law-of-large-numbers averaging: ~250k+ candidates/job, i.e. ~650ms of work at
the measured ~2.6us/candidate -- doesn't fit even a soft-scale (100ms)
period. Worse, the problem is WORST at low U (small Q means fewer candidates
fit per job), not best -- so there's no U-range where pure batch-averaging
rescues it.

**Resolution (discussed with Silvia, confirmed)**: treat this as a real,
documented per-workload noise floor (same philosophy as the existing
tight-scale matmul calibration floor, [[rq1_calibration_noise_floor]]), not
a bug to eliminate. `CV_THRESHOLD` made env-overridable in `calibrate.py`
(previously hardcoded 0.02; now `float(os.environ.get("CV_THRESHOLD", 0.02))`,
matching the convention `run_job.sh` already used for its own per-cell gate).
Pass `CV_THRESHOLD=0.3` (or similar) when calibrating/running primes cells.
Some very-low-U tight-scale cells may end up genuinely uncalibratable even
with a loosened threshold -- expected, will show up as skipped cells with an
explicit reason, not silently faked data.

**Harness changes needed: none.** `generate_yaml.py`, `calibrate.py`,
`run_job.sh` were already fully generic over the `WORKLOAD` string (a
pre-existing design decision, confirmed by reading all three) -- switching
workload name is purely `WORKLOAD=primes` at invocation time. Only
functional code change needed was the `CV_THRESHOLD` env-override above.
