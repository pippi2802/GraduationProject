# Backlog — 2026-08-13

## Meeting with academic supervisor — notes

### 1. Research question reframing: desktop → cores → cloud

Shift focus from application-level (desktop) framing toward computation-level
(cores) and cloud framing. Under this reframing, the isolated-setup work
already done (stable core isolation enabling RT workloads on Azure) plus the
new `dra-rt-driver` v1.0.0 (`RequestedCpus`, controlled core placement)
together should be elevated into their own research question, roughly:

> How do you achieve controlled, predictable computation placement for
> real-time workloads in cloud VMs?

The isolated setup and v1.0.0 become the *answer* to this question, not just
infrastructure supporting other RQs.

### 2. Workload change: ptrchase → prime number computation

Matmul stays as-is. Ptrchase is replaced with a prime-number-computation
workload, to introduce a genuine data-dependency component alongside pure
computation. Requirement: keep the same reproducibility property ptrchase
had — for a given U, the number of operations must stay controlled/fixed
(deterministic op count), so the experiment stays reproducible even though
the workload is now data-dependent.

Supervisor referenced HPC libraries that ship "precooked" tasks as a possible
source for this (name not captured — follow up).

### 3. Application-domain framing for workload choice

Two angles to justify workload choice under the RTS application domain:
- **Application/task-domain angle**: possibly adopt or reference a precooked
  task/workload from an existing HPC-oriented library, giving the workload a
  recognizable "model setup" grounded in a known task type rather than a
  synthetic microbenchmark.
- **RT-domain angle**: also keep a workload representing the classic RT
  case — respond to an event, lightweight, not heavy computation — as a
  contrasting/complementary case to the heavier HPC-style task.

### 4. Model3 / model3-w2 burst analysis: need causal explanation

Current results describe *that* bursts happen and correlate with alpha
crossing 1, but not *why* alpha increases at that point. Need to identify the
actual mechanism driving the alpha increase in each case — e.g., garbage
collection, kernel housekeeping, cache/TLB effects, scheduling overhead —
rather than stopping at "alpha increased, therefore burst."

### 5. Model4 redesign: periodic vs. event-triggered task models

Rather than continuing to add more multi-concurrency variants to model4,
pivot to comparing two fundamentally different task activation models:

- **Periodic model**: tasks sit in a run queue, generally ordered by
  earliest release/deadline, activated on a timer.
- **Event-triggered model**: task activation is driven by an external
  trigger/event rather than a clock.

Goal: analyze release jitter under each model, identify what it's
attributable to (expected to matter most in the event-triggered case), and
explore whether/how it can be reduced. This feeds into the broader question
of what an RT-kernel suitable for cloud deployment would need to get right.

### 6. Bigger-picture direction: RT-suitable kernel for the cloud

Open design question to resolve: is a task a thread, or not — i.e., what the
execution unit backing a task should be. Existing RTOS options are largely
edge-device-oriented; the question is whether an OS/kernel purpose-built for
RT-in-cloud (as opposed to RT-on-edge) is a distinct, worthwhile design
target. Supervisor referenced microkernels as a relevant architecture
direction, and the general idea of a simulated RT-operating-system running
"conceptual jobs" — building a custom RT-model capable of running both
event-driven and time-driven jobs, structured around the Hollywood
principle / callback principle ("don't call us, we'll call you" — inversion
of control, event-driven dispatch rather than polling).

Central question this direction is aiming at: can an OS run in the cloud in
a genuinely predictable manner?

### 7. Practical/system-level question

How should an application be configured against the driver (`dra-rt-driver`)
so that the resulting system is predictable end-to-end — i.e., what's the
general guideline/pattern for going from "application code" to "predictable
placement + execution," not just the mechanics of one experiment.

### 8. RT task representation at the C level

RT tasks are generally represented with a `while`/`do` loop structure. For
the release/activation path specifically, need to identify how much
"administration" (scheduling/bookkeeping overhead) is required per release,
and minimize it — i.e., treat per-release administrative overhead as a
quantity to reduce in pursuit of predictability.

### 9. Reference material

Supervisor provided `docs/01 Tasks.pdf` (Johan Lukkien, "Operating Systems,
Concurrency and Time" — task/job formal model: static attributes
tau_j, C_j, T_j, phi_j, D_j; dynamic per-job attributes est, dl, b, e;
derived quantities U_j, lateness, tardiness, slack, response time;
soft/firm/hard deadline classes; explicit note that tasks are not threads or
processes — tasks are mapped onto those eventually). This last point is
directly relevant to point 6's "is a task a thread" question — worth
grounding that discussion in this existing formal vocabulary rather than
reinventing terms.
