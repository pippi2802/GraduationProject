## Built today

**Node-reuse workflow for scenarios `02`/`03`/`06`**: rather than creating fresh
namespaces/directories from the pristine `model1`/`model5-phys` templates every time,
copied (`cp -r`, never `mv` — keeps prior scenarios' data intact as historical record)
the most recently-freed combo's workload dir, fixed `namespace:`/`app:`/
`experiment-model:`/`host_path` via `sed`, relabeled the physical node's
`experiment-model` k8s label, created a fresh namespace, and redeployed `apply.sh`.
Established discipline: **always restore the previous scenario's lever to full
baseline before applying the next one** — skipping this on `06-model1`/`06-model5`
(reused from `01`, isolcpus still stripped) caused a real `FAIL: isolcpus still
active` in `verify_scenario.sh` until `01_isolcpus_only.sh restore` was run first.

**`08_freq_unpinned.sh`** — new 8th scenario, added on the user's request after
observing calibration's tight-scale cv problems raised the general question of
frequency-pinning sensitivity. Subtractive like `01`-`06`, but mechanically different:
frequency pinning isn't grub-based, it's set live by `agent-daemonset.yaml.template`'s
init container every time `rq1-agent` starts (governor→`performance`, turbo off,
min=max freq), gated by `apply.sh`'s `SKIP_FREQ_PIN`. So `apply()` resets governor to
the real distro default (`schedutil`/`ondemand`, read from
`scaling_available_governors`, never hardcoded), re-enables turbo/boost, un-pins
min/max freq — and the namespace's agent then needs a separate redeploy with
`SKIP_FREQ_PIN=1` so it doesn't silently re-pin itself on its next restart. No reboot
needed (unlike `01`/`02`/`03`/`06`). Added a matching `freq_unpinned` case to
`verify_scenario.sh`.

**Calibration order fixed: soft now runs before tight in every `config.yaml`.**
`calibrate.py` iterates `cfg["scales"].items()` in file order, and `tight` was always
first — meaning every fresh `k_table.json` build put tight's calibration through the
node's least-settled state (right after a scenario's reboot + fresh calib-pod
creation), while soft calibrated second, effectively for free once things had
settled. Swapped `tight:`/`soft:` line order in all 14 `config.yaml` files
(`workloads/*/config.yaml`) via a small Python pass — no code change needed, dict/YAML
insertion order does the rest.

## Real bugs found and fixed

1. **Grub corruption bug, real root cause finally found (retroactively explains the
   `01-model1` corruption from 2026-09-13 too).** `01_isolcpus_only.sh`,
   `02_nohz_full_only.sh`, and `03_rcu_nocbs_only.sh` all stripped their target token
   via `re.sub(r'\s*TOKEN=\S+', '', line)`. `\S+` is greedy and matches *any*
   non-whitespace character — including the line's closing `"` when the stripped
   token happens to be the **last** one before it (e.g. `...rcu_nocbs=1,2,3"` →
   strips `rcu_nocbs=1,2,3"`, closing quote included, leaving an unterminated
   string). `grub-mkconfig`/`update-grub` then fails with `Syntax error: Unterminated
   quoted string`, but the *staged* file looks superficially fine unless you actually
   check quoting (I missed this once myself, mid-session, and called a broken file
   "already correct" because I'd only checked that the target token was gone).
   Reproduced and hit live on `03-model1`/`03-model5` (rcu_nocbs was the last token on
   isolate-core.sh's line) — full recovery both times (restore `grub.rq1.orig`,
   rebuild the whole baseline stack from scratch, re-apply with the fixed regex).
   `02-model1`/`02-model5` turned out fine despite the same old buggy script, purely
   by luck of token position: `nohz_full=` sits in the *middle* of the baseline line,
   so the regex's greedy match stopped at the following space, never reaching the
   quote. `06_boot_params.sh` was never affected — its three stripped tokens are fixed
   literal strings with no `\S+`, so nothing to over-match. Fixed all three regexes to
   match only the value charset (`[0-9,-]+`, same charset their own `status()`
   functions already used for `/proc/cmdline` greps) instead of `\S+`.
2. **`verify_scenario.sh`'s `thp_always()` checked for the wrong "default."** Assumed
   the distro default was `[always]`; this platform's real default (confirmed
   empirically post-reboot on `07-model1`, once THP forcing was genuinely removed) is
   `[madvise]`. Not a real OS-state problem — a false-negative in the check itself.
   Fixed to assert "not `[never]`" instead of "is `[always]`".
3. **`rt-k8s-worker-1` had a typo'd node label**: `experiment-model=06-model` (missing
   the trailing `5`) instead of `06-model5` — silently left its `rq1-agent`
   DaemonSet with zero matching nodes (0 pods, no error), until caught via
   `kubectl get nodes --show-labels`.

## Replicated finding: isolcpus/root-domain RT-bandwidth effect confirmed on 2 more nodes

Following up on 2026-09-15's root-domain/DEADLINE-fair-server finding: every node
where isolcpus stayed **active** (`04-model1`, and now `06-model1`/`06-model5`,
across two completely different other-lever-removed scenarios — systemd-containment
and boot-params respectively) seeds to the same **~940000/1000000 (94%)** RT ceiling.
Worker-0 (`01-model1`, isolcpus **stripped**) seeds to **~790003 (79%)**. Same binary
split regardless of which *other* lever is removed — only isolcpus removal moves the
number. This is now a 3-node replication (5 once `02`/`03` are checked), not a
single-node anecdote — solid material for the thesis' RQ1/RQ3 write-up.
