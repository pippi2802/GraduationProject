## Real bugs found and fixed

1. **Path double-prefixing after the restructure** — `run_job.sh`'s `results/` and
   `node-prep/steer-irqs.sh` references, and `node-prep/apply.sh`'s `../models/` reference,
   needed fixing since they now live one level differently relative to what they point at.
   Caught via `bash -n` + manual trace, not via failure at runtime.
2. **`.gitignore` stale** after the directory move — still pointed at the old
   `RQ1_final/.venv`/`analysis/data` paths, not the new nested ones.
3. **`verify_scenario.sh`: `[ -s FILE ]` is the wrong test for sysfs files.** Files like
   `/sys/devices/system/cpu/isolated` always contain a trailing newline even when the
   reported list is empty, so file *size* is never actually 0 — `-s` always reported
   "active" regardless of real content. Fixed by checking the command-substituted string
   (`[ -n "$(cat FILE)" ]`, which strips the newline) instead of file size. This silently
   made every `isolcpus_only`/`nohz_full_only` verification wrong until caught.
4. **`04_systemd_contain.sh`: early-return guard checked the wrong thing.** `apply()`
   checked whether the drop-in *file* existed before clearing — but `systemctl
   set-property` sets a *live* property independent of the file, so if a prior run had
   already removed just the file, the guard skipped the actual live-property clear
   entirely. Fixed by always running the clear unconditionally (idempotent, safe either way).
5. **Grub file corruption on `01-model1`'s node** — an earlier (pre-fix) run of the
   additive-design script left a truncated, unterminated `GRUB_CMDLINE_LINUX="..."` line
   in `/etc/default/grub`. Recovered by restoring from the original pristine backup
   (`grub.rq1.orig`, created by `isolate-core.sh`'s very first run days ago) and rebuilding
   the full stack from scratch rather than trying to patch around the corruption.
6. **DRA driver's `NodeAllocationState` accumulates orphaned claims — no reconciliation.**
   The real blocker, still unresolved. Deallocation only happens via the graceful
   `kubectl delete` → kubelet → driver handshake. A node reboot, or `pkill` on `run_job.sh`
   mid-cell, kills the pod without that handshake ever firing, leaving the claim marked
   allocated in the CRD forever with nothing actually using it. Found stale entries on
   3 of 6 workers initially (utilization numbers matching real values from the sweep —
   30%, 40%, 50%, 10%, 20% — confirming they're leftover from cells that were live during
   today's many reboots, not from the original clean `kubedeadline-experiments` collection
   weeks ago). Restarting the controller/kubeletplugin pods does **not** clear this — it's
   persisted in etcd, not pod memory. First cleanup attempt used JSON Merge Patch
   (`{"allocatedClaims":{}}`), which is a no-op for clearing a map under RFC 7386 semantics
   — silently didn't work. Corrected with JSON Patch (`--type=json`, explicit `remove` per
   UUID), which did work. But then confirmed **every subsequent `pkill` mid-run creates a
   new orphaned entry**, and it spread to a previously-clean worker (`worker-4`, backing
   `05-model1`) during this session's own retry cycling.
