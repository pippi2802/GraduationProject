# Backlog — 2026-09-03

## nohz_full verification — found the right counter, then found a real bug

**Goal**: Johan's question ("are your cores private, only responding to your
timer interrupt?") plus general due diligence on the isolation stack — is
`nohz_full` on the isolated cores (1-3, worker node) actually suppressing the
periodic scheduler tick, or just configured on paper?

**Wrong counter first, caught and corrected.** First check used
`/proc/interrupts`'s `LOC:` line (the traditional LAPIC local-timer
interrupt) — read 0 on every core, including core 0 (not `nohz_full`,
should tick normally). Zero on a core that should definitely be ticking was
the tell that `LOC` was the wrong thing to look at, not evidence of anything
real. Root cause: this kernel runs as a Hyper-V guest and uses Hyper-V's own
paravirtualized synthetic timer, not a bare-metal LAPIC — confirmed via
`dmesg` (`hyperv_clocksource_tsc_page`/`hyperv_clocksource_msr`) and
`systemd-detect-virt`/`lscpu`/`/sys/bus/vmbus/devices`. The actual counter to
watch is the `HVS:` line ("Hyper-V stimer0 interrupts").

**Correct check**: two snapshots of `grep "^HVS" /proc/interrupts` 5 seconds
apart, per-core delta, while a real paced round is running on core 2.

**First result (looked like a real finding, wasn't the full story)**: core 2
delta = 5,010 over 5s ≈ **1002/sec**, i.e. ticking at a plain 1000Hz rate —
one to two orders of magnitude above what the periodic workload itself would
ever need (tight scale ≈ 20/sec, soft scale ≈ 2/sec). Cores 1 and 3 (idle,
isolated, nothing scheduled): delta = 0. Read at face value this looked like
`nohz_full` silently failing to engage on core 2, possibly a Hyper-V
clock-device limitation (`nohz_full` needs the underlying clock-event device
to support real one-shot mode; a paravirt `stimer` was a plausible suspect).

**Real root cause, found via `ps`**: `ps -eo pid,ppid,psr,stat,cmd` on core 2
turned up two leftover shell processes, state `R` (runnable) — `sh -c 'while
:; do :; done'`, pinned to core 2. These were diagnostic busy-loop load
generators from an earlier steal-time stress test in this same session,
never actually killed afterward (run at least twice, hence two PIDs, 7864
and 8061). `nohz_full`'s precondition is **exactly one runnable task on the
core at all times** — a second, permanently-runnable process on the same
core violates that continuously, so the tick keeps firing to arbitrate
between them. This wasn't a kernel/Hyper-V limitation at all; it was
self-inflicted contamination from our own earlier debugging.

**Confirmed the fix**: `kill 7864 8061`, then re-ran the same HVS delta
check over another 5s window: 4,585,086 − 4,584,756 = **329 over 5 seconds
≈ 66/sec** — a **15x drop** from ~1002/sec, immediately after killing the
two processes. `nohz_full` is working close to as intended once the actual
interference is removed. The remaining ~66/sec is still somewhat above the
workload's own theoretical wake-up rate, but small enough (15x better,
mostly explained) that it wasn't worth chasing further this session — noted
as a small residual, not reopened.

**Data consequence**: any round collected while the busy-loops were still
alive is contaminated — this specifically affected `noaslr_round1`, which
was running at the time. Flagged for re-collection from scratch once the
interference was confirmed removed, rather than trusted as-is.

## Conditions for `nohz_full` to actually suppress the tick (for the writeup)

- Requires exactly one runnable task on the isolated core at all times —
  the moment a second process becomes runnable there (even briefly), the
  tick resumes to arbitrate, silently, with no error/warning anywhere.
- At least one CPU in the system must stay in normal periodic-tick
  ("housekeeping") mode — the kernel needs somewhere driving jiffies-based
  timekeeping, scheduler accounting, and RCU grace-period detection. Putting
  every CPU into `nohz_full` isn't supported; this is closer to a hard
  constraint than a convention.
- The right verification counter depends on the underlying clocksource —
  don't assume `LOC:` (LAPIC local timer) applies on every platform. On this
  Hyper-V-guest kernel, the tick is delivered via `HVS:` ("Hyper-V stimer0
  interrupts") in `/proc/interrupts`, not `LOC:`.
- Verification method: two timestamped snapshots of the relevant
  interrupts-line counter, a few seconds apart, taken while a real paced
  round is active on the core under test — a single snapshot is meaningless
  since the field is cumulative since boot.
