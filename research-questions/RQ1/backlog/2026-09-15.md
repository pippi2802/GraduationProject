## Real bugs found and fixed

1. **Root cause of the day's "target not Ready" failures across all 6 OS-sensitivity
   namespaces: a stale `app:` label.** `os-experiments/workloads/{01,04,05}-{model1,model5}/job.yaml`
   still had the literal label copied from the original template (`app: model1`,
   `app: model5-phys`) instead of the directory's own name. `run_job.sh` waits on
   `kubectl wait -l "app=$MODEL,role=target"` where `$MODEL` is the directory name
   (e.g. `01-model1`) — searching for a label no pod ever had, guaranteeing every
   attempt times out at 120s regardless of actual cluster health. This was masked for
   a long time by several other real, concurrently-present problems (see 2026-09-13's
   entry: orphaned `NodeAllocationState` claims, the driver's `PendingAllocatedClaims`
   in-memory leak, crash-looping kubeletplugin pods) that got fixed first but weren't
   the actual primary blocker. Fixed all 6 `job.yaml` templates' `labels:` line and
   regenerated all manifests under `generated/`.
2. **Round1/round2 results silently overwritten.** The original 6 full-sweep launch
   commands never set `OUT_TAG`, so both rounds wrote to the identical path
   (`results/<model>/<scale>/U*/jobs.csv`, overwritten with no versioning). Only the
   *log* filenames were tagged `_round1`/`_round2` — not the actual data destination.
   Round1 data for any cell round2 also completed is unrecoverable. Going forward:
   always set `OUT_TAG=_round1` / `OUT_TAG=_round2` explicitly.
3. **Full cluster reboot mid-session** (all namespaces' restart counters, including
   `etcd`/`kube-apiserver` on the control plane, clustered to the same ~7-8 minute-old
   window) — consistent with the known "VMs get deallocated" Azure behavior. Left 3 of
   6 `dra-rt-driver-kubeletplugin` pods and 3 `calico-node` pods in
   `Init:Error`/`Init:CreateContainerConfigError`.

## Real finding: `isolcpus` removal structurally caps achievable utilization (~0.79 vs ~0.94)

Empirically, `01-model1`/`01-model5` (scenario `01_isolcpus_only`, isolcpus stripped
from the baseline) fail to admit any cell at U≥0.8, while `04-model1`/`05-model1`
(isolcpus still present) complete the full sweep including U0.94. Root-caused via
`setup/scripts/rt-budget-seed.sh`, a pre-existing project script that seeds the root
and `kubepods.slice` cgroups' RT bandwidth ceiling, dynamically clamped to each node's
free `SCHED_DEADLINE` budget.

- Confirmed via raw manual cgroup writes that the *kernel*, not the driver, rejects
  U≥0.8 writes on the isolcpus-stripped node (`echo "8000 2" > cpu.rt_runtime_us`
  succeeds on an isolated node, fails `Invalid argument` on the stripped one).
- Read `/sys/kernel/debug/sched/debug`'s `dl_bw` stats on both a stripped node
  (worker-0, backing `01-model1`) and a still-isolated node (backing `04-model1`):
  - worker-0 (isolcpus stripped): `total_bw=209712` (~20%) uniformly across all 4 cpus
    — merged into one root domain.
  - 04-model1's node (still isolated): `total_bw=52428` (~5%) on cpu0 (housekeeping,
    its own small domain), `total_bw=157284` (~15%) on cpus 1-3 (the isolated domain,
    where the target's live `SCHED_DEADLINE` reservation actually runs —
    `dl_nr_running=1` confirmed on cpu2).
- Verified `rt-budget-seed.sh`'s exact formula against its source
  (`free_us = (bw - total_bw) * RT_PERIOD / 1048576`, then `RT_RUNTIME = free_us - 10000`
  margin, sampled from `grep -m1` = the *first* `dl_rq` entry in debugfs = cpu0 only):
  reproduces both nodes' seeded values exactly (940000 for 04-model1, 790003 for
  worker-0). The script's own header comment already documents "~0.79 where the
  fair-server holds 0.20" and "worker-0 gets ~0.75" as its own reference example —
  this finding corroborates, rather than contradicts, the script author's prior
  characterization.
- Mechanism: `total_bw` (the kernel's DEADLINE fair-server / CFS-starvation-safety
  reservation) is tracked per root domain and scales with that domain's cpu-count
  membership, not as a fixed fraction of the whole machine. `isolcpus` partitions cpus
  into a separate root domain from the housekeeping cpus; stripping it merges them back
  into one shared domain, growing the fair-server reservation the merged domain needs,
  which lowers the free `SCHED_DEADLINE` budget available to any single H-CBS/KubeDeadline
  reservation on that node.
- Task-level scan (full `chrt -p` sweep over every live PID) found **no** difference
  between the two nodes — identical kernel FIFO housekeeping threads
  (`migration/N`, `idle_inject/N`, `watchdogd`, irq threads), both `system.slice`/
  `user.slice` at `rt_runtime_us=0`. Rules out "extra hidden workload" as the cause;
  confirms it's specifically the root-domain/fair-server accounting effect above.

This is real, citable material for RQ1/RQ3: isolation state doesn't only reduce
runtime interference — it changes root-domain topology, which changes how much
DEADLINE bandwidth the kernel's own CFS-safety mechanism reserves, which directly
caps the maximum feasible utilization any single reservation can request on that
node. Worth a limitation/finding note: `01_isolcpus_only`'s U≥0.8 cells are not
achievable data points on this hardware — not missing data to chase further, but a
structural ceiling to report and explain.
