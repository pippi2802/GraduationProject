## Done today

**model3/model3-w3 ptrchase — root cause found and fixed**
- `aligned_alloc` crash (`[probe] ptrchase alloc failed`) traced to `generate_yaml.py`'s `INTERFERER` template missing `securityContext.capabilities: [SYS_NICE, IPC_LOCK]` (present on `NEIGHBOUR`/`COMPETITOR_RESERVED`, never on `INTERFERER`). Without `IPC_LOCK`, `mlockall(MCL_FUTURE)` can't lock the 128MB ptrchase buffer under the node's default `RLIMIT_MEMLOCK`, so the allocation fails with `ENOMEM`.
- Fixed in `generate_yaml.py`; verified live on w3's node (interferer ran 80s+, 766 rows, `kind=ptrchase buf_kb=131072`, no crash).

**model4 designed and built end-to-end**
- Reviewed the reference KubeRay/PyTorch experiment (same `rt.resource.example.com` CRD as our harness — likely the predecessor evaluation). Decided against replicating it wholesale (metric mismatch: no periodic-release/deadline-miss structure; confound explosion: Ray scheduler, network, PyTorch thread pool) and against IRQ steering (already-built but narrower, likely-negative result on Azure).
- Locked design: single H-CBS reservation (`count=2`), workload split across 2 pthreads running **concurrently** each period (batch-of-2, mirroring the authors' "one task per batch, dispatched in parallel" logic), forced onto **two distinct physical cores only** — no sibling arm, deliberately dropped to avoid model3's biggest source of debugging pain.
- Claim: *does model1's single-thread deadline/tardiness guarantee hold when the reservation's own workload is split across 2 concurrent threads on 2 physical cores* — plus the matmul-vs-ptrchase angle: *does memory contention cause higher deadline-miss than compute contention even in this intra-reservation context.*
- Built: `matmul.c` `--threads N --cpu-list <list|env>` batch mode (barrier-synchronized pthreads, one row per batch, `--threads 1` byte-for-byte unchanged — verified locally for both matmul and ptrchase); `Makefile` (`-lpthread`); `models/model4/config.yaml`/`job.yaml`/`README.md` rewritten (`target_threads: 2`, `RtClaimParameters count: 2`, own image tag `v3` so model1-3's cached `v2` is untouched); `run_job.sh` placement retry now rejects SMT-sibling landings, physical-only. `generate_yaml.py`/`calibrate.py` needed no changes — confirmed model4 correctly reuses model1's existing `k_table.json`.
