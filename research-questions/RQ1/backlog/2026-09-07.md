## Isolation test: vanilla PREEMPT_RT works fine on this exact VM/hypervisor

Before chasing H-CBS further, tested whether the hang is RT+Hyper-V in
general, or specific to H-CBS's kernel build. Ubuntu ships an official
PREEMPT_RT kernel via the open `Universe` repo (`ubuntu-realtime` package,
no Ubuntu Pro entitlement needed for this — Pro is only required for
long-term security updates on it, confirmed directly after `pro
enable realtime-kernel` failed with "not entitled" on this subscription
tier):
```
sudo add-apt-repository universe && sudo apt update
sudo apt install ubuntu-realtime
```
Produced `linux-image-5.15.0-1032-realtime` (Canonical's own 5.15.78-based
build, close to the KubeDeadline paper's claimed 5.15.105).

First boot attempt into it panicked immediately (`VFS: Cannot open root
device ... error -6`, kernel panic at 0.9s) — unrelated to RT: Azure's
`GRUB_FORCE_PARTUUID` initrdless fast-boot trick (`/etc/default/grub.d/
40-force-partuuid.cfg`) only works for kernels with storage drivers built
directly into the image, which this generic package doesn't have. Disabled
that file, regenerated grub, retried — **booted clean**: `uname -a` showed
`5.15.0-1032-realtime ... PREEMPT_RT`, `/sys/kernel/realtime` = 1, real
load average, network/SSH reachable. Confirms PREEMPT_RT itself is not
fundamentally incompatible with this Hyper-V VM — the H-CBS-specific hang
is a property of H-CBS's own kernel build, not RT+Azure in general.

## Root-caused the Hyper-V config divergence, attempted the fix, hang persisted

Diffed the working Canonical `.config` against H-CBS's hanging `7.0.0+`
`.config` for Hyper-V-related options: on the working kernel, `CONFIG_
HYPERV`, `CONFIG_HYPERV_VMBUS`, `CONFIG_HYPERV_STORAGE`, `CONFIG_
HYPERV_UTILS`, `CONFIG_HYPERV_BALLOON`, `CONFIG_PCI_HYPERV*` are all
modules (`=m`); on H-CBS's kernel they're all built-in (`=y`). Mechanically
plausible: built-in drivers initialize during early `do_initcalls`, in the
same window PREEMPT_RT's percpu allocator/RCU are still stabilizing;
modules defer that init to after boot settles, via initrd.

Attempted to flip H-CBS's config to match. Found `CONFIG_HYPERV` itself is
declared `bool` (not `tristate`) in this kernel's `drivers/hv/Kconfig` —
can only ever be `y`/`n`, never `m`, a real difference from Canonical's
older 5.15 tree where it was still tristate. Confirmed the four sub-drivers
(`HYPERV_VMBUS`, `HYPERV_STORAGE`, `HYPERV_UTILS`, `HYPERV_BALLOON`) and
`PCI_HYPERV`/`PCI_HYPERV_INTERFACE` are still independently `tristate` even
with the bool-locked parent — fixed via `scripts/config --module <name>`
(sed pattern-matching against stale `.config` text had silently failed
twice first, a real lesson: always re-derive current state before a
targeted edit, don't assume prior text format holds).

Rebuilt (`make -j$(nproc) bindeb-pkg`, ~43min; a first attempt hit a
deterministic `objcopy`/`libz.so.1.2.11` segfault building an unrelated
Broadcom driver module — confirmed not memory pressure (`free -h` showed
4.5GB free, no OOM-killer activity in `dmesg`) and not file corruption
(`dpkg -V zlib1g` clean) — a flaky toolchain interaction under `-j4`
parallelism; a plain incremental retry succeeded cleanly, confirming it was
non-deterministic/unrelated to the actual test). Installed the new kernel
(`7.0.0`, essential packages only — skipped waiting on the slow
single-threaded `-dbg` packaging step again, ~20-30min for ~1.3GB of debug
symbols, not needed to boot). One-time-booted into it via `grub-reboot`.

**Same hang, identical to before**, confirmed via live boot-diagnostics
serial log: `Created slice Slice for Azure VM Agent and Extensions` then
silence — byte-for-byte the same stall point as the original incident.

**Why the fix didn't work, and why that's actually informative**:
`CONFIG_HYPERV_TIMER` (the Hyper-V synthetic-timer clocksource,
`sysvec_hyperv_stimer0`) has to stay built-in regardless — clocksources
cannot be deferred to a loadable module, the kernel needs a working timer
before it can load modules at all. The original stall trace (`systemd`
stuck in `pcpu_alloc_area`, `rcuc/0` blocked on `rt_spin_lock` in
`free_percpu`, alongside a STIMER interrupt) was always rooted in this
specific always-built-in piece, not in the VMBUS bus driver we
successfully modularized. The hypothesis was directionally correct (a
built-in driver racing PREEMPT_RT's altered locking during early boot) but
identified the wrong specific subsystem — and the actual culprit can't be
fixed by a config flip at all, by kernel architecture, not by choice.

## Mechanism, understood clearly now

PREEMPT_RT is a kernel-wide locking-model change, not a scheduler-only
patch: it converts nearly every `spinlock_t` across the *entire* kernel
into a sleepable `rt_mutex`, kernel-wide, to cut worst-case latency. Any
code written assuming the old atomic/non-blocking spinlock semantics (safe
anywhere, including hard-IRQ context) can break once its locks are
converted, if it's called from a context where sleeping isn't actually
safe. H-CBS's own scheduler patches (`rt.c`/`deadline.c`/`core.c`) are not
implicated at all — the break is in Hyper-V's STIMER timer-init code,
completely unrelated, just compiled into the same kernel. That code was
never audited/fixed for RT-safety in H-CBS's tree. Canonical's own
real-time kernel almost certainly *has* had this fixed, because Canonical
explicitly sells/supports "Real-time Ubuntu on Azure" as a real deployment
scenario (their own blog post: "production-ready on Intel Atom/Core
processors," an official supported Azure image path) — someone there had
to do that audit for a real customer-facing feature. Nobody maintaining
H-CBS's tree has needed or tested that specific combination.
