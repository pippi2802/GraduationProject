## RQ1_final: new workload + full scaffolding, scoped to model1 only

Per Johan's suggestion (sieve, not the existing trial-division primes kind)
and the decision to also attempt PREEMPT_RT, started a new, deliberately
separate `research-questions/RQ1_final/` tree -- explicitly not touching
anything in `RQ1/` -- scoped to model1 only for now.

**`workload.c`** (new) -- single-threaded periodic path only (no
event/batch/multi-kind modes, no pthreads), same 17-column CSV schema as
`matmul.c` so `analysis_lib.py` reads it unmodified. Design decisions made
explicitly, not assumed:
- **SCHED_FIFO, not the reference literature tool's default `SCHED_DEADLINE`**
  (checked the downloaded `PeriodicTask-master` reference project's
  `rt_utils.c` directly -- its `sched_set()` uses native `sched_setattr`
  with `SCHED_DEADLINE`, which would bypass H-CBS's cgroup bandwidth
  mechanism entirely and test the kernel's own EDF/CBS class instead, a
  different mechanism than RQ1 studies). Placed under H-CBS via the same
  DRA-claim mechanism as every other model.
- **Both `CLOCK_MONOTONIC` and `CLOCK_REALTIME` supported via `--clock`** --
  the reference tool uses `CLOCK_REALTIME` (NTP-adjustable) for
  `clock_nanosleep`; `matmul.c` deliberately uses `CLOCK_MONOTONIC`. Rather
  than pick one silently, exposed both so the difference itself can be
  measured.
- **`mlockall(MCL_CURRENT|MCL_FUTURE)` included** -- validated as real
  literature practice by finding it in the reference project's own
  `make_rt()`, not just assumed.
- Sieve of Eratosthenes over a fixed bound (`SIEVE_N=8192`), repeated `K`
  times per job -- deterministic op count, no data-dependent branching
  (unlike the existing trial-division primes kind), dominated by a
  scattered/stride-increasing memory-write pattern instead. A third,
  distinct workload profile alongside matmul's arithmetic and primes'
  branch-heavy trial division.

Compiles clean (`-Wall -Wextra`), smoke-tested both clock modes directly.

**Scaffolding** (new, all trimmed to model1's actual needs, not copied
verbatim from RQ1's multi-model versions): `Makefile`/`Dockerfile`/
`build.sh` (image `pippina2/rq1final-probe:v1`), `calibrate.py` (~140 lines,
core K-search logic kept, multi-kind/workload branching dropped),
`generate_yaml.py` (287 → ~45 lines, all co-runner/neighbour/competitor
template logic dropped -- model1 has none), `run_job.sh` (1027 → ~180
lines, same cut), `models/model1/{config.yaml,job.yaml}` (own namespace
`rq1final-model1`, own `host_path`, own image -- zero collision risk with
RQ1's own running experiments). `node-prep/` copied over near-verbatim from
RQ1 (`apply.sh`, `isolate.sh`+core, `harden.sh`+core, `isolation-audit.sh`)
since those were already model-agnostic, parameterized by `<model>` +
config.yaml lookup -- no RQ1-specific hardcoding found in any of them.

Not yet built out: `calibrate.py`/`generate_yaml.py`'s actual adaptation
tested against a real cluster (no RQ1_final cluster exists yet).

## PREEMPT_RT: built, confirmed active, then hit a real reproducible hang

Long saga, worth recording precisely since it cost most of the day.

**Kernel rebuild, first attempt**: cloned `HCBS-patch`
(`https://github.com/Yurand2000/HCBS-patch.git`, branch
`rt-cgroups-multi-260514`, pinned to the exact commit
`ae5a2b404e3aebfdba8a8513091377a2022302df` already baked into the running
kernel's own package version string) on the dev VM (`rt-ubuntu`). Copied the
running kernel's `.config` as the base (not a fresh/default config, to avoid
silently dropping Azure/Hyper-V driver config), added
`CONFIG_EXPERT=y`+`CONFIG_PREEMPT_RT=y` via `scripts/config`, confirmed with
`RT_GROUP_SCHED=y` unaffected (no `depends on !PREEMPT_RT` guard on it in
this tree -- checked directly). Built with `LOCALVERSION=-rt` (necessary --
the package version is git-commit-hash-derived, not config-derived, so
without an explicit local-version override the new build would have
silently overwritten the existing `linux-image-7.0.0+` package in place
instead of installing alongside it).

**Booted successfully, PREEMPT_RT confirmed genuinely active** -- not just a
version-string label: the boot log itself showed `SMP PREEMPT_RT` in the
version banner, plus RCU messages unique to real PREEMPT_RT builds
(`Preemptible hierarchical RCU implementation`, `RCU priority boosting:
priority 1 delay 500 ms`, `RCU_SOFTIRQ processing moved to rcuc kthreads`).

**Then, on a later boot, a genuine kernel hang** -- an RCU stall detected at
~60s into boot, well before cloud-init or networking start. `systemd` (pid
1) stuck mid-`clone()` syscall inside the percpu allocator
(`pcpu_alloc_area`), right as a Hyper-V timer interrupt
(`sysvec_hyperv_stimer0`) fired; the RCU callback kthread (`rcuc/0`) blocked
in `rt_spin_lock` inside `free_percpu`. This is a real PREEMPT_RT-specific
locking pathology (`rt_spin_lock` is PREEMPT_RT's actual schedulable,
priority-inheriting lock, not a busy-wait), not a config mistake --
searched for a known matching upstream issue (percpu allocator + RCU stall
+ Hyper-V + PREEMPT_RT); found related-but-not-identical reports (a
resolved case with the same *symptom* on a different hypervisor entirely --
ARM/vtimer masking, not Hyper-V) and one general, real PREEMPT_RT gotcha
(RT-priority tasks can starve RCU kthreads) that doesn't obviously apply
here since the stall happened in plain early boot, before any RT workload
was running. No confirmed fix found; this is being treated as "retry and
see," not "known bug, apply patch X."

**Recovery detour**: an accidental second `waagent -deprovision+user
-force` (likely a stale-history re-run) locked out SSH again; Serial
Console itself then failed to connect at all (`168.63.129.16` NSG rule
missing -- fixed); once connected, confirmed the hang directly from the
live boot log rather than guessing from connectivity symptoms alone.
Attempted in-place GRUB-menu recovery via Serial Console (select the
working `7.0.0+` entry manually during the boot countdown) -- not reliably
catchable in time. Fell back to `az vm repair create`/`restore` (the
disk-copy-to-a-throwaway-repair-VM technique, since a disk still referenced
as a VM's OS disk cannot be attached elsewhere directly, even deallocated
-- learned this the hard way after a manual `az vm disk attach` was
rejected with `ConflictingUserInput`).

**Decision**: not worth finishing the `rt-ubuntu` recovery. Retrying the
PREEMPT_RT build fresh instead, on a new VM deployed from the existing
Compute Gallery image (version `1.0.0`, the known-good non-RT HCBS
baseline) rather than from bare Ubuntu -- avoids redoing the whole HCBS
kernel install from scratch. In progress as of end of day; if the same
stall recurs on a fresh VM, that's real evidence this is a reproducible
platform/kernel-commit interaction, not an instance-specific fluke.
