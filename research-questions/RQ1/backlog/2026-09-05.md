# Backlog — 2026-09-05

## OS-isolation hardening batch: built the tooling, measured the actual impact

Following up on the isolation-audit discussion (what does the setup actually
buy us, beyond `isolcpus`/`nohz_full`/`rcu_nocbs`), built two new node-prep
scripts and ran a real before/after comparison rather than just confirming
config changed.

**`node-prep/harden.sh` + `harden-core.sh`** (new) — same nsenter-via-agent
technique as `isolate.sh`. Four actions: `systemd-contain` (hard cgroup
clamp of `system.slice`/`user.slice` to `keep_cpu` only, via `AllowedCPUs=`
-- deliberately NOT touching `kubepods.slice`, since target/competitor pods
live there), `irq-steer` (parks every device IRQ on `keep_cpu`, installs a
systemd oneshot unit so it re-applies every boot, since `/proc/irq/*`
resets regardless of anything else), `boot-params` (`mitigations=off
transparent_hugepage=never`, later extended with `rcu_nocb_poll`, batched
onto the same grub line `isolate-core.sh` already uses, made per-token
idempotent so adding a new token later doesn't require re-touching what's
already applied), `smt-off` (deliberately NOT run this session -- shared
nodes across models, would risk model2/3's own SMT-sibling experimental
design; model1's baseline still has a structurally-present, if idle, SMT
sibling as an explicit, acknowledged residual).

**`node-prep/isolation-audit.sh`** (new) -- `snapshot <label>` /
`report <a> <b>`, measures (not just confirms) impact: nohz_full tick rate
(5s HVS delta), non-idle % on cores 1-3 (60s `mpstat`), IRQ count delta,
THP/compaction events, a `getpid()` syscall-overhead microbenchmark, and
`hwlatdetect`. One real bug fixed live: once `systemd-contain` is applied,
the *user's own shell* is under `user.slice` and gets hard-clamped too --
`taskset -c <core>` from that shell then fails with `EINVAL`. Fixed by
running the benchmark under `systemd-run --scope --slice=-.slice`, which
places it directly under the (never-restricted) root cgroup instead.

## The actual comparison data (vanilla → nodeprep → hardened → hardened2)

- **Tick rate**: 47/sec (vanilla, but idle-window artifact — ordinary
  `NOHZ_IDLE` already does this for free on any idle core, not `nohz_full`'s
  real contribution) → 0 (nodeprep). The number that actually demonstrates
  `nohz_full`'s value is Thursday's (2026-09-03) measurement taken during a
  *live* paced round: 1002/sec → 66/sec, a real 15x reduction.
- **Non-idle % / IRQ counts**: already at floor (0.00%, near-zero) by the
  `nodeprep` stage, *before* `systemd-contain`/`irq-steer` ran. Their
  measured incremental contribution in this data is ~0 -- not because
  they're wrong, but because `isolcpus` alone already removed everything
  measurable here. Their real value is structural (closing the
  explicit-affinity gap `isolcpus` can't cover), not a further reduction.
- **Syscall overhead** (the one metric that moved a lot, in an
  unexpected-at-first direction): 0.1047us/call (vanilla) → 0.1689us/call
  (nodeprep, +61%) → 0.1629us/call (hardened, -3.6% off nodeprep). Matches
  a known, real mechanism: `nohz_full` re-arms the tick on every kernel
  entry/exit, making every syscall more expensive even though the periodic
  tick itself disappears -- the same effect already implicated in the
  2026-08-14 primes K-recalibration incident, now directly quantified.
  `mitigations=off` claws back a small amount of that cost, as expected,
  but doesn't come close to closing the gap since `nohz_full`'s re-arm cost
  is the dominant term. `rcu_nocb_poll` (hardened2: 0.1655us/call) showed
  no further measurable effect -- flat within noise.
- **hwlatdetect**: moved inconsistently across both comparisons (max latency
  and samples-exceeding-threshold disagreed in direction once, agreed but
  both got worse once) at only 10-19 samples per 30s run. Too small a
  sample to attribute to any specific config change; recommended re-running
  at `--duration=120`+ before treating either direction as real. No
  plausible mechanism connects `rcu_nocb_poll` (software RCU notification)
  to SMI-detected hardware latency at all, so that particular swing is
  almost certainly host-level noise, not caused by the config change it
  happened to follow.
