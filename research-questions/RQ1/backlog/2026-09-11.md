## Multicore experiment (model5) — built today

**Design question resolved**: "multicore" had two readings — (A) many independent
reservations packed onto a node concurrently (what the `kuberay-test-main` reference repo
actually does — N separate single-core claims, no join), vs (B) one claim spanning multiple
cores serving threads of the same task. Went with a variant of B: **one `count:2` claim, two
concurrent compute threads sharing both reserved cpus**, rather than two separate claims —
this is what's actually untested by the existing model3 arms (which test two *separate*
reservations contending), and it's a small extension of model4's existing claim shape.

**Feasibility spike, before committing to the build** (`models/model4` scratch, cleaned up):

- Traced the DRA driver's `count` handling (`allocations.go`): `count:2` sets up two
  *independent* per-cpu CBS budgets under one claim (`cpuPartitioning(..., count, "worstFit")`,
  same runtime/period each), not a pooled multi-cpu budget.
- Traced the actual kernel patch tree (`~/Documents/rt-k8s/HCBS-patch`, not just the Go
  driver): confirmed a dedicated `fe38bf70a587 "multi: MultiCPU HCBS"` commit plus a cluster of
  RT-cgroup migration commits (push/pull `dl_server` semantics) — multi-cpu migration within one
  H-CBS cgroup is a deliberately engineered kernel feature, not incidental behavior.
- Confirmed no cgroup-level `cpuset` restriction exists anywhere in the DRA driver or CDI path
  — today's cpu confinement is 100% the application's own `taskset` call. Important for anyone
  else touching this: nothing else stops a thread from running anywhere on the node if the app
  doesn't pin itself.
- Live test on `rt-k8s-worker-5` (`m4` namespace): a single thread on a `count:2` claim never
  migrated (200/200 samples on one cpu) — expected, no contention means no push/pull reason to
  move. Two concurrent threads sharing the same claim's mask **did** migrate (both threads
  observed on both reserved cpus under contention). Confirms floating is real on this stack,
  but only manifests under genuine contention, matching standard Linux RT scheduler semantics.

**Built**: `models/model5-phys/` and `models/model5-smt/` — K=2 concurrent compute threads
(balanced, no oversubscription yet) on one `count:2` claim, `requestedCpus` hardcoded per the
model1/model4 placement-forcing fix precedent (2026-09-09):

- `model5-phys`: cpus `[1,3]`, cross-physical-core pair — control arm.
- `model5-smt`: cpus `[2,3]`, SMT sibling pair — expected to show contention effects.

Reuses `workload.c`, tight/soft scales, and the existing calibration/generation pipeline
unchanged — no source or `run_job.sh` changes needed. K=3/K=4 (genuine oversubscription, more
threads than reserved cpus) is a follow-up: duplicate the directory, add one more `taskset`
block to `job.yaml`'s args.
